# Conduct

A screenplay records behaviour: the device hears this, says that, shows something. Conduct is the consistent pattern behind many such choices. It is what you design; the screenplay is one instance of it.

## The file

`design/devices/<device>/conduct.md`:

```
---
name: Night light
voice: Ash
---
- At night it never speaks first; a dim light shows that something is waiting.
- Speaks quietly and briefly, one sentence at a time.
- …
```

- `name`: what the group calls the device.
- `voice`: one name from the voice catalogue in `VOCABULARY.md` (Ash, Theo, Sam, Noor, Mira, Wren).
- Then **five to eight rules**, one per line, each starting with `-`.

## Seven dimensions

Every conduct takes a position on these, whether it says so or not. A good set of rules covers most of them.

- **Initiative**: when it speaks first and when it waits.
- **Amount**: how much it says.
- **Register**: plain, formal, playful, in images or metaphors.
- **Withholding**: what it leaves unsaid or unshown.
- **Address**: whom it speaks to when several people are present.
- **Uncertainty**: how it handles its own doubts and mistakes.
- **Relationship**: servant, companion, guardian, colleague.

The channels count too: when it uses the screen instead of its voice, what the light does, whether it makes a sound.

## Good rules and weak rules

A good rule says what the device does, in a way that decides a situation you have not written yet. A weak rule describes a character or a wish.

| Weak | Good |
| --- | --- |
| Is friendly. | Addresses the patient by first name and thanks people for waiting. |
| Respects privacy. | Never says private content aloud when someone else is in the room; shows it on the screen instead. |
| Is helpful. | Answers questions about the care plan it can see, and offers the next step. |
| Doesn't talk too much. | Speaks one sentence at a time and stops when someone else starts talking. |
| Is careful with medical things. | Does not answer medical questions; offers to call the nurse. |

Test a rule by asking: could two people, reading it, write the same line for the device? If not, make it more concrete.

## Rule and instance

The conduct is the rule; the performance is an instance. When a performance feels wrong, decide which one is wrong:

- **The line is wrong, the rule is right**: the performance broke its own conduct. Fix the line.
- **The line follows the rule, and it still feels wrong**: the rule is wrong. Change the rule, then write the performance again.

Changing a rule changes every performance of that device. That is the point: you design the behaviour, not the lines.
